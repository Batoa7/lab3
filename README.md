## SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
| --- | --- | --- | --- |
| Performance | /cart/add latency | p95 < 200мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь | ≥ 90% | 2 мин, 10с зогсолт орсон |

### Босго сонгосон үндэслэл

Серверийн код дотор /pay-д ~5% алдаа зориудаар суулгасан тул 8% гэдэг нь бодит, боломжийн босго (5%-иас арай өндөр зөрүү үлдээж, санамсаргүй хэлбэлзлийг тооцсон). Performance-ийн 200мс нь localhost орчинд өгөгдлийн сан хандалтгүй, энгийн endpoint-д зохимжтой босго. Availability-ийн 90% нь 10 секундийн доголдол 2 минутын цонход хэр зэрэг нөлөөлөхийг тооцсон эхлэлийн тоо.

### Error budget тооцоо (Availability)

2 минутын цонхонд 90% гэдэг нь: 120 секунд × (1 - 0.90) = **12 секундийн "эвдрэх эрх" (error budget)**.

## k6 Threshold код (Алхам 4)

SLO хүснэгтийн 3 босгыг `slo-test.js`-д k6 threshold болгон кодчиллоо. Endpoint бүрийг `tags: { name: ... }`-аар ялгаж, `thresholds`-д тус тусад нь заасан:

- `http_req_duration{name:cart}`: `p(95)<200` — Performance SLO
- `http_req_failed{name:pay}`: `rate<0.08` — Reliability SLO
- `checks`: `rate>0.90` — Availability SLO

Нэмэлт (4 дэх) threshold болгож `/report`-д `http_req_duration{name:report}`: `p(95)<450` нэмсэн.

### PASS үр дүн (results/pass.txt)

Хэвийн нөхцөлд (сервер тасралтгүй ажиллаж байх үед) `k6 run slo-test.js` ажиллуулахад бүх 4 threshold PASS болов:

| Threshold | Босго | Бодит үр дүн | Дүгнэлт |
| --- | --- | --- | --- |
| checks (Availability) | rate > 90% | 98.62% | PASS |
| http_req_duration{name:cart} (Performance) | p95 < 200мс | 14.06мс | PASS |
| http_req_duration{name:report} | p95 < 450мс | 403.1мс | PASS |
| http_req_failed{name:pay} (Reliability) | rate < 8% | 4.13% | PASS |

Localhost орчинд `/cart/add` ихэвчлэн 1-15мс-д хариулдаг тул `p(95)<200` threshold нь бодит дарамт өгдөггүй "сул" босго байж болзошгүй; харин `/report`-ийн `p(95)<450` нь серверийн зориудаар суулгасан 200-400мс хүлээлттэй ойролцоо тул илүү бодитой хэмждэг.

## Chaos туршилт (Алхам 5)

Тестийн duration-ыг 2 минут болгож ('2m'), тест ажиллаж байх үед серверийг зориудаар унагасан (Ctrl+C), 10 секунд хүлээгээд дахин асаасан.

### Үр дүн (results/chaos.txt)

| Threshold | Босго | Бодит үр дүн | Дүгнэлт |
| --- | --- | --- | --- |
| checks (Availability) | rate > 90% | 83.97% | FAIL |
| http_req_duration{name:cart} | p95 < 200мс | 6.58мс | PASS |
| http_req_duration{name:report} | p95 < 450мс | 394.56мс | PASS |
| http_req_failed{name:pay} | rate < 8% | 18.81% | FAIL |

### Бодит availability тооцоо (хүсэлтээр)

Амжилттай хүсэлт / Нийт хүсэлт = (5691 - 912) / 5691 = 4779 / 5691 ≈ **83.97%**

### Яагаад цагаар тооцсон 12с budget ба хүсэлтээр гарсан үр дүн зөрж байна вэ?

Алхам 3-т 2 минутын цонхонд 10 секундийн зогсолтыг ЦАГААР тооцвол ~8.3% (120с-ийн 10с) "эвдрэх эрх" гэж үзсэн. Гэвч бодит алдааны хувь 16.02% гарсан бөгөөд энэ нь хоёр дахин их байна. Учир нь сервер унасан үед хүсэлт шууд (connection refused) буцдаг тул хэвийн үеийн /report-ийн 200-400мс хүлээлт алга болж, зогсолтын 1 секундэд хэвийн ажиллаж байх үеийнхээс хамаагүй олон хүсэлт "багтдаг". Иймд цагаар тооцсон 8.3% нь хүсэлтээр хэмжихэд бараг 2 дахин өссөн хэмжээгээр илэрдэг.

### Reliability threshold яагаад мөн FAIL болсон бэ?

http_req_failed{name:pay} мөн FAIL болсон (18.81%), учир нь сервер унасан үед /pay-д илгээсэн бүх хүсэлт амжилтгүй болдог (connection refused нь алдаа гэж тооцогддог). Иймд нэг availability эвдрэл availability болон reliability хоёр SLI-г зэрэг зөрчиж байна. Хоёр SLI-г тусгаарлахын тулд reliability-г зөвхөн сервер идэвхтэй ажиллаж байх үеийн 500 error rate-аар хэмжиж, connection-refused тохиолдлыг зөвхөн availability metric-д тооцох боломжтой.

## Threshold зориуд эвдэх (Алхам 6)

`slo-test.js`-г хуулж `slo-test-fail.js` үүсгээд, `/report`-ийн threshold-ыг `p(95)<450`-аас **`p(95)<100`** болгож өөрчилсөн. Сервер `/report`-д 200-400мс хооронд хариулдаг тул энэ threshold ямар машин дээр ч найдвартай FAIL болно.

### Үр дүн (results/fail.txt)

| Threshold | Босго | Бодит үр дүн | Дүгнэлт |
| --- | --- | --- | --- |
| checks (Availability) | rate > 90% | 98.66% | PASS |
| http_req_duration{name:cart} | p95 < 200мс | 3.83мс | PASS |
| http_req_duration{name:report} | p95 < 100мс | 393.83мс | **FAIL** |
| http_req_failed{name:pay} | rate < 8% | 3.99% | PASS |

Гаралтын сүүлд k6 дараах алдааг өгсөн:

### Exit code

```bash
k6 run slo-test-fail.js 2>&1 | tee results/fail.txt; echo "exit=${PIPESTATUS[0]}"
```

Гарсан exit code: **`exit=99`**. Анхны `echo "exit=$?"` командаар шалгахад буруу `exit=0` гарсан — учир нь pipe (`|`) ашигласан тул `$?` нь k6-ийн биш, сүүлчийн команд (`tee`)-ийн exit code-ыг буцаадаг байсан. `${PIPESTATUS[0]}`-ыг ашигласнаар k6-ийн жинхэнэ exit code (99)-ыг зөв авсан. CI pipeline яг энэ exit code-оор build амжилттай/амжилтгүйг шийддэг тул зөв аргаар шалгах нь чухал.



## Дүгнэлт

Энэ лабораторид сценариог SLO болгож, SLO-г k6 threshold код болгон хөрвүүлэх бүтэн замыг өөрөө туулсан. Хамгийн хэцүү хэсэг нь чанарын сценарио дахь "Хэмжүүр"-ийг тодорхой тоон босго болгон буулгах явдал байсан — ялангуяа localhost орчинд бодит дарамт өгдөг тоо сонгох (жишээ нь /cart/add-ийн 200мс threshold нь бодит орчинд хэт сул байсан бол /report-ийн 450мс нь бодитой хэмжигдсэн). SLO хүснэгт дэх босго ба slo-test.js доторх threshold ижил байх ёстой гэдэг шаардлага нь баримт бичиг болон код хоёрын хооронд зөрүү гаргахгүй байхын ач холбогдлыг ойлгуулсан. Chaos туршилт нь availability сценариог хэсэгчлэн баталсан — сервер зогсоход availability threshold FAIL болсон нь зөв (сценариод заасан ёсоор), гэхдээ error budget-ийг ЦАГААР урьдчилан тооцсон (12 секунд, ~8.3%) нь бодит байдал дээр ХҮСЭЛТЭЭР хэмжихэд хамаагүй их (16.02%) гарсан. Энэ зөрүү нь маш сургамжтай байсан — учир нь сервер унасан үед хүсэлт агшин зуур connection-refused болж буцдаг тул зогсолтын нэг секунд хэвийн секундээс хамаагүй олон хүсэлт "иддэг" болохыг нүдээр харах боломжтой болсон. Мөн нэг chaos эвдрэл хоёр өөр SLI (availability, reliability)-г зэрэг зөрчиж болохыг олж харсан нь эдгээр metric-үүдийг тусгаарлан хэмжих аргачлалын хэрэгцээг ойлгуулсан. Threshold-оо зориуд эвдэх алхам дээр pipe ашигласан үед `$?` нь буруу exit code (tee-ийн) буцааж болохыг олж мэдэж, `PIPESTATUS[0]`-ыг ашиглах шаардлагатайг сурсан — энэ нь CI/CD дээр build амжилттай/амжилтгүйг зөв тодорхойлоход маш чухал практик мэдлэг. Ерөнхийдөө энэ лаб нь SLO зөвхөн онолын тоо биш, харин бодит систем дээр хэмжигдэж, автоматаар шалгагдаж, зөрчигдвөл pipeline-ыг зогсоох чадвартай "гэрээ" гэдгийг ойлгоход тусалсан.
